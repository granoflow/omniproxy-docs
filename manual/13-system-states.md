# 启动与连接故障

遇到错误先判断停在哪一层：App 能否打开、网关能否运行、来源能否连接、模型能否完成请求。处理最先失败的一层，比重复更改所有设置更有效。

| 看到的状态 | 先做什么 |
| --- | --- |
| 仍在加载 | 先等当前任务完成，避免并行启动第二份实例 |
| 需要目录访问或模型位置离线 | 重新连接磁盘并通过正式目录选择器授权 |
| 内部数据迁移需要处理 | 保留旧数据，运行当前版本提供的诊断并按提示处理；不要直接删除数据库 |
| Runtime 未启动或连接中断 | 查看当前错误与诊断，确认 App/CLI 实例身份，再使用正式重试入口 |
| 端口冲突 | 查明占用者，调整自己正在测试的实例，不强制退出身份不明的服务 |
| 来源未验证 | 回来源页测试当前地址和凭据 |
| 模型需要重新测试 | 对当前模型和调用方案重新测试 |

## 网关地址不能访问

从监控台重新复制地址。确认工具和网关的位置：工具在另一台机器、容器或远程环境时，它的 `127.0.0.1` 不是你的 Mac。使用其支持的网络连接方式，并核对网关监听范围与认证。

不要先关闭认证或开放所有接口来排除问题。先用同机、已知支持的最小请求确认入口，再排查跨设备网络。

## 认证、额度和能力错误

认证错误先分清是网关代理密钥还是供应商 API key。目录能列模型但生成失败时，检查模型权限、余额、速率限制、协议和能力。图像、语音及工具调用需要各自实际支持，不能由文本聊天成功推断。

## 取得诊断信息

App 中可到“设置”→“关于”→“报告问题”，点击“生成报告”。报告在本机生成，包含版本、系统信息、当前 Runtime 快照和界面已有错误；它不读取全部历史日志或调用账本。先查看内容，再按需要使用“保存报告”或“复制报告”；“写邮件”只打开邮件流程，发送前仍要检查收件人和正文。

独立 CLI 先用 `omniproxy doctor --help` 查看支持的检查，再用 `omniproxy doctor --output json` 查询诊断。它针对该 CLI 实例，不是对当前 App 的检查；先读 `ok` 和具体结果，失败保留错误码。

macOS 需要查监听端口时，可以在终端只读查看。例如网关实际端口为 56788：

```sh
lsof -nP -iTCP:56788 -sTCP:LISTEN
```

把端口替换成你实际看到的值，检查进程名和 PID。没有输出不一定证明端口绝对空闲，也可能受权限影响；看不清归属时不要执行退出或终止命令。该检查不会自动修复冲突。

## 更新或恢复前

保存具体错误、版本和操作时间。备份只保留有恢复价值的配置或数据，先确认目标与恢复方式；不要把移动模型权重当成已经备份来源凭据。旧数据迁移、覆盖和删除都必须按当前工具实际范围操作。

仍不能解决时，通过设置中的报告入口提供最小复现、错误和已经做过的检查。去掉密钥、原文、个人路径与附件，不上传整个工作数据目录来代替诊断。

内部数据迁移错误不提供通用的手工修库步骤。App 尚能进入设置时，按上文“取得诊断信息”生成 App 报告；进不了工作台时，保留启动窗口的完整错误与版本，通过正式支持渠道提交，不删除或改名数据库来强行进入。独立 CLI 的 `doctor` 只诊断 CLI 实例，不能拿它替 App 修库。此时的完成动作是保留数据并提交明确错误，而不是自行完成未提供的迁移操作。
